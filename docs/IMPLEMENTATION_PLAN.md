# 日程助手实施计划

## 1. 项目目标

根据 `prototypes/main-window.png`、`prototypes/add-task-dialog.png` 和 `prototypes/presentation-canvas.png` 实现一款本地优先的桌面日程待办提醒软件。首版重点是还原原型中的日历、日/周视图、日程维护和系统提醒，并保证数据在应用重启后仍然保留。

## 2. 实施假设与范围

| 项目 | 首版约定 |
| --- | --- |
| 运行形态 | Windows 桌面应用，后续可扩展 macOS |
| 技术方案 | Wails 3 + Go + React + TypeScript + Vite |
| 版本策略 | 固定经过验证的 Wails 3 Beta 版本和 Go/NPM 依赖，不自动跟随最新版 |
| 数据存储 | Go 数据访问层 + SQLite；首版不依赖服务器 |
| 提醒方式 | Go 后台调度器 + Wails 原生系统通知，支持多个提前提醒时间 |
| 页面适配 | 优先精确适配原型的 1200×800 桌面窗口，兼容 960×640 及以上尺寸 |
| 首版边界 | 不包含账号体系、云同步、多人协作、移动端和复杂重复规则 |

### 技术方案对比

| 方案 | 优点 | 代价/风险 | 结论 |
| --- | --- | --- | --- |
| Wails 3 桌面端 | 复用系统 WebView2，支持 React/Vite；Go 后端开发和跨语言调用较直接；安装包与内存较小 | 当前仍处于 Beta，需要固定版本并增加回归测试 | **首选**，在资源占用与开发效率之间最均衡 |
| Tauri 2 桌面端 | 生态和权限模型较成熟，安装包小、资源占用低 | 需要 Rust 工具链，团队学习和调试成本较高 | 稳定性优先时的备选 |
| Electron 桌面端 | 全 TypeScript 开发，通知和打包生态成熟 | 携带 Chromium，安装体积和常驻内存明显较高 | 交付速度极端优先时的备选 |
| WinUI 3 | Windows 原生通知、后台能力和 MSIX 集成最好 | 仅支持 Windows，且无法复用 React 技术栈 | 明确不做跨平台时的备选 |
| PWA/Web | 部署简单、跨平台 | 浏览器关闭后提醒可靠性不足，权限与后台任务受限 | 不适合作为本地提醒软件首版 |

## 4. 数据与架构设计

### 分层职责

| 层级 | 主要职责 |
| --- | --- |
| Wails 应用层 | 窗口生命周期、托盘、单实例、开机启动、系统通知和应用事件 |
| Go 领域与服务层 | 日程 CRUD、SQLite 事务、提醒调度、休眠恢复、去重和数据迁移 |
| Wails 绑定层 | 仅向前端暴露经过校验的 Go 方法和类型，统一转换错误，不暴露任意文件或命令执行能力 |
| React 渲染层 | 月历、日/周视图、表单、详情弹层、交互状态和错误展示 |
| 前端领域层 | 月历生成、时间轴布局、视图状态和表单校验；关键规则在 Go 层再次校验 |

### 推荐目录结构

| 目录 | 内容 |
| --- | --- |
| `frontend/src/components` | 月历、时间轴、弹窗、表单等可复用组件 |
| `frontend/src/features` | 日程、提醒、设置等按业务划分的前端模块 |
| `internal/domain` | 日程实体、值对象和领域规则 |
| `internal/service` | 日程服务、提醒调度器和应用用例 |
| `internal/repository` | SQLite 仓储实现、事务和数据迁移 |
| `internal/platform` | Wails 通知、托盘、开机启动、单实例和系统事件适配 |
| `build/windows` | 图标、清单、NSIS/MSIX 配置和签名脚本 |

### 首版核心数据模型

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | UUID |
| `title` | string | 日程名称，必填 |
| `startAt` / `endAt` | ISO datetime | 起止时间，按本地时区录入并持久化 |
| `location` | string? | 会议室、线上会议或其他地点 |
| `color` | string | 日程边框和标记颜色 |
| `reminderOffsets` | number[] | 提前分钟数，如 `[15, 60]` |
| `status` | enum | `pending`、`completed`、`cancelled` |
| `createdAt` / `updatedAt` | ISO datetime | 审计时间 |

## 5. 开发计划表

> 以 1 名熟悉 React/TypeScript、具备基础 Go 经验的全栈开发者为基准，预计 8～11 个工作日完成可安装的 MVP，其中包含 Wails 3 Beta 的兼容性缓冲。

| 阶段 | 预计工时 | 主要任务 | 交付物 | 完成判定 |
| --- | ---: | --- | --- | --- |
| 1. 工程初始化 | 0.5～1 天 | 建立 Wails 3/Go/React/TypeScript 工程；固定依赖版本；配置代码规范、测试和打包脚本 | 可运行的桌面应用骨架 | `wails3 dev` 启动成功，Go 与前端构建无错误 |
| 2. 设计系统与外壳 | 1 天 | 提取颜色、间距、字体、阴影；实现标题栏、侧栏和主内容区 | 与原型一致的静态主窗口 | 1200×800 下关键尺寸和层级接近原型，无溢出 |
| 3. 日历与日程领域模型 | 1 天 | 月历算法、Go 领域模型、Wails 类型绑定、校验、SQLite 仓储接口和测试 | 可切换月份的月历及本地 CRUD | 月份边界、闰年、跨日时间和仓储测试通过 |
| 4. 日视图与周视图 | 1.5 天 | 时间轴、日程定位、重叠布局、视图切换和待办列表联动 | 可交互的日/周日程视图 | 新增测试数据后位置、长度、颜色和联动正确 |
| 5. 新建/编辑交互 | 1.5 天 | 日程弹窗、日期时间选择器、多选提醒、详情、编辑和删除 | 完整日程维护流程 | 新增、修改、删除、完成状态均可用且实时同步 |
| 6. 持久化与提醒 | 1.5 天 | SQLite 迁移与事务、Go 提醒调度、系统通知点击处理、重启和休眠补偿 | 重启可恢复数据并按时提醒 | 多提醒不重复、不漏发；删除和完成后能取消待触发提醒 |
| 7. 桌面系统集成 | 1～1.5 天 | 托盘、窗口销毁/重建、单实例、开机启动、NSIS 打包和 WebView2 策略 | 可长期驻留的 Windows 应用 | 关闭窗口后仍能提醒，二次启动聚焦现有实例，安装卸载正常 |
| 8. 测试与视觉验收 | 1～1.5 天 | Go 单元/集成测试、前端组件和流程测试、截图对比、Beta 兼容性回归 | 自动化测试集、Windows 安装包和中文交付文档 | 核心流程通过，干净环境可安装启动，关键界面完成原型复刻 |

## 7. 关键风险与应对

| 风险 | 影响 | 应对策略 |
| --- | --- | --- |
| Wails 3 仍处于 Beta | 桌面 API 或打包流程可能出现回归 | 固定验证过的版本和 Go 模块校验；升级单独建分支并执行完整回归 |
| 应用完全退出后无法由普通调度器提醒 | 可能漏发提醒 | MVP 关闭窗口时销毁 WebView、Go 进程驻留托盘；启用可选开机启动 |
| Windows 休眠期间错过触发点 | 唤醒后提醒延迟 | 每次启动/唤醒重新扫描，补发仍在容忍窗口内的提醒 |
| 夏令时或时区变化 | 提醒时间偏移 | 统一存储 ISO 时间并保留本地时区语义，覆盖时区变更测试 |
| 同一时间多日程重叠 | 时间轴遮挡 | 使用列分配算法并设置最小宽度，超量时聚合展示 |
| SQLite 文件损坏或迁移失败 | 应用无法启动或数据丢失 | 事务迁移、启动前备份、完整性检查和可回滚迁移 |
| WebView2 缺失或版本异常 | 界面无法启动 | NSIS 携带 WebView2 Bootstrapper，干净 Windows 10/11 环境验证 |
| 未签名安装包触发 SmartScreen | 用户不信任或无法顺利安装 | 内测允许未签名；公开发布前接入可信代码签名并在 CI 中验证 |
| 原型未定义完整交互 | 开发中出现体验分歧 | 以“可发现、可撤销、可验证”为原则补齐详情、删除确认和空状态 |

## 9. 首版完成定义（Definition of Done）

- 三张原型中的主界面、新建弹窗、日期时间选择器和提醒多选均已实现。
- 月历、待办列表、日视图和周视图使用同一份数据并保持同步。
- 日程可新增、查看、编辑、删除、完成，错误输入会被阻止并给出中文提示。
- SQLite 数据重启后保留，提醒可在 Go 进程驻留期间可靠触发，休眠唤醒后可恢复调度。
- 主窗口关闭时释放 WebView，托盘驻留状态的目标内存不高于 70 MB；实际阈值以首轮基准测试校准。
- Wails 3、Go 模块和 NPM 依赖均锁定版本，生产包能够在干净 Windows 10/11 环境运行。
- 核心领域逻辑、组件交互和主流程具备自动化测试。
- Windows 安装包可在干净环境安装、启动和卸载，交付文档为中文。

## 10. 后续迭代建议

MVP 稳定后，再按价值依次考虑重复日程、托盘快捷新增、数据导入导出、日历订阅（ICS）、跨设备同步和团队协作。这样可以先验证“快速记录 + 准时提醒”这一核心闭环，避免首版被账号、服务器和同步冲突处理拖慢。
